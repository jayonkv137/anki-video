# Monday-Start UX Workflow

1. **Understand existing flows:** Since your system logic is fixed, start by mapping *information architecture and user flows*. Write out each phase’s key screens or steps (you can skip formal personas/research since you *are* the expert user). Document the conversation states, approval gates, and outputs. In practice, make a simple flowchart or use ASCII/mermaid diagrams to lay out each task path.  
2. **State inventory:** List every UI *state* you need – e.g. gate = {open/blocked/locked}, artifact = {drafting/generating/ready/out-of-date}, action buttons = {disabled vs active vs loading}. Record how states transition (your state machine). Many new AI‐aided design workflows even automate “UI Implementation Contracts” and state inventories for you. At minimum, tabulate “object – possible states – visible cues/labels” so nothing is overlooked.  
3. **Lo-fi screen sketches:** On paper or simple HTML/CSS prototypes, sketch each screen’s layout and major elements (wireframes). Don’t worry about style yet – just ensure the content blocks and navigation make sense. This catches missing pieces early. Skip formal “job story” docs; instead write short notes or bullet job tasks inline with your sketches if needed.  
4. **Design tokens & fundamentals:** Before finalising visual designs, define your core style tokens. Choose a **typography scale**, base font sizes and line-heights that match a dense interface (for example, a smaller base size or tighter scale than a marketing site). Pick a **spacing rhythm** (e.g. 4px or 8px grid) that lets you pack data yet keep a clear hierarchy. Set your **color palette** – usually a neutral background (light or dark) with one or two accent colors for actions and states. In other words, give the system some “point of view” beyond generic defaults. (See below for examples from pro tools.) You can do this early as a brand-style sketch or derive tokens as you refine screens.  
5. **Build components & screens:** With tokens in hand, craft your UI components (buttons, inputs, dialogs, etc.). An “atomic design” approach works: capture all existing UI elements (buttons, tables, cards), group them into atoms/molecules. Then lay out full screens using these components. Iterate – refine layouts and spacing so that related data is grouped tightly and key actions have breathing room. As you design screens, publish or export components into a live design-system (e.g. Claude Design project or your own CSS library).  

 Throughout, reuse patterns and the tokens you defined. Some teams build the design system *in parallel* with high-fidelity screens (setting colors and fonts first, then assembling pages). Others extract tokens *from* finished mockups. Either is fine; the key is consistency and a single source of truth for styles.

# Design System Starting Kit (Dense Professional UI)

- **Type Scale:** Use a compact but legible scale. For a dense UI, base text might be 14px (or even 12px on large monitors), with headings stepping up modestly. Ensure each level has clear contrast. In practice, professional tools often use smaller text and tighter line-heights than consumer sites. E.g. issue trackers like Linear or code editors use 12–14px for body text, whereas a marketing site might use 16px+.  
- **Spacing Rhythm:** Adopt a fine-grained grid (4px or 8px base). Most design systems use 4px multiples; experts tend to cluster data, so default margins can be smaller (e.g. 8px), with larger gaps (16–24px) reserved for major sections or between panels. Crucially, use whitespace to **group** related items and **separate** unrelated ones. In essence, “silence” (empty space) should guide the eye.  
- **Colour & Elevation:** Use a muted background (light grey or dark grey) so your dense content pops. Limit primary colors to a few – perhaps one brand accent (blue or green) for primary buttons/statuses, one for warnings (yellow/orange) and error (red). Avoid decorative gradients or heavy shadows; pro tools often use subtle borders or very soft shadows to delineate panels. For example, a DAW like Ableton Live uses a dark grey theme with bright green highlights; a terminal/IDE uses a dark background and high-contrast text. Study tools like Visual Studio, Premiere Pro or Blender: they favour grey palettes with colored highlights. Whichever palette you choose, stick to it strictly. These choices set your UI’s character.  
- **Density & Hierarchy:** Emphasise hierarchy deliberately. A common AI pitfall is *uniform look* – everything the same weight. Don’t do that. For example, a critical alert or “Approve” button should be larger or brighter than secondary options. Use icons judiciously for quick recognition, but accompany them with text labels (AI UIs often pick meaningless icons). Real dense interfaces (e.g. spreadsheets, DAWs, IDEs) rely on typography, layout and selective color rather than fanciful graphics. Consider “desktop” cues: keyboard focus rings, tooltips, status bars. Ensure primary action buttons stand out and have enough padding. Tables or lists of repeated data can be compact (small padding, tight rows), but put extra space around section breaks and important controls. In short, design every detail (borders, iconography, focus states) *purposefully* so the interface reads as crafted.  

## Reference Inspirations
- **DAWs (e.g. Ableton, Pro Tools):** heavy use of grids/lines, mono-color backgrounds, collapsible panels. They pack many sliders/knobs with small labels and rely on color-coded tracks to distinguish channels.  
- **NLEs (Adobe Premiere, DaVinci):** panel-based layout (timeline at bottom, preview top, sidebars for tools). Use thin borders and tabs. Text is small; critical controls have icons.  
- **3D software (Blender, Maya):** highly dense, keyboard shortcut-driven. Accepts clutter but uses grouping and color-toning to keep it readable.  
- **Terminals/IDEs (VSCode, iTerm):** monospaced fonts, minimal UI chrome. Colors for syntax are inspired by cognition (e.g. red=error, green=success). Interface chrome is often collapsible.  
- **Figma/Linear (UX tools):** relatively clean but assume user knows shortcuts. Key actions (like “Play” or “New Item”) are prominent. Sidebars use consistent spacing and icons with text. Notice how Figma’s layers panel or Linear’s issue list use subtle dividers and hover states to manage density. **Steal**: Figma’s use of clear fonts and intuitive icons; Linear’s neat table/list layout for text-heavy content.  

# Claude Design Round-Trip (Concrete)

Claude Design uses a **two-layer model**: a *Design System* project and *Screens/Projects* that instantiate it. In practice, you **create the design system first**, publishing your color palette, typography and UI parts (buttons, cards, etc.). Once published, you can attach it to your project. On disk, the design system lives in a `_DES/` folder alongside your HTML/CSS screens, showing the parent–child relationship: “this project uses that design system.”  

- **Editing:** In claude.ai/design, you use the chat or canvas to define tokens and components. You can tweak colors/typography via chat and watch live updates. When satisfied, hit **Publish** to finalize the system as a library.  
- **Syncing with Code:** To integrate with your repo, use Claude Code’s `/design-sync` skill. This invokes the Claude Design API to “list_projects”, “get_file”, etc.. For example, you might run a CLI command that pulls down the latest `_DES/` folder contents into your code. Each component has a preview card (an image) registered via the API so you can see it in the design system viewer. Crucially, design-sync works incrementally: it plans changes per-file, not a one-time dump. That means you can update a button style in claude.ai/design, run `write_files` to push only that component code to your repo, without breaking everything. (One note: the word “project” appears twice – one refers to design system vs. the code project. The API `list_projects` lists design system libraries, not your product screens.)  
- **Round-Trip Example:** Suppose you code a component `<Button>` in your app, then in claude.ai/design choose “Create from code” to import your React/Tailwind component as a design part. Claude Design reads the repo via MCP and auto-generates the style (color, padding) into a design system component. You refine it there and publish. Back in code, `design-sync` can then fetch the updated style (e.g. new color token, new spacing) and update your CSS. The reverse also works: tweak tokens in Design and send updates into code.  

**Dev vs Figma:** Because your stack is plain HTML/CSS, you’re essentially using Claude Design as a lightweight design system IDE. You don’t *need* Figma frames for pixel-perfect preview. Claude Design can export HTML or ZIPs of your code components. However, Figma is still useful for exploration: you might prototype a visual style or icon layout in Figma (or Figma Make) to get ideas, then implement in CSS. But unlike a typical design-driven workflow, here the **source of truth is code tokens**. Think of Figma (or Figma Make) as a sketchpad or polish tool, not the system’s bottleneck. In fact, if your UI has dozens of interactive states, traditional Figma artboards struggle (they capture one state per frame). In summary: use Claude Design + code for the system and final screens, use Figma for quick experiments or brand style exploration.

# Designing Interface **State**

A complex tool’s UI is really a collection of states. Good practice is to design *each meaningful state* (and how to transit between them) and document them in your component library or prototypes. For each screen element, ask: what if it’s inactive, loading, empty, error, success, locked, etc. Designers conventionally use these patterns:

- **Loading/Busy:** Show spinners or skeleton placeholders. Buttons that trigger actions should enter a **loading state** (often with a disabled style and a spinner). Never leave a button “sinking” with no feedback – AI outputs often miss this.  
- **Disabled/Locked:** If an action isn’t available (e.g. gate locked, insufficient permissions), use the classic **disabled style**: greyed-out control with no hover state. Accompany it with a tooltip or icon to explain why it’s disabled (e.g. a padlock icon and “Requires approval” text). This follows UX norms and avoids surprise. As one UX expert points out, hiding premium/locked features is worse than showing them clearly. If a button leads to a paid feature, mark it with a lock or currency icon **before** the click, not after.  
- **Warnings vs Errors:** Distinguish advisory tips (Yellow/Orange, non-blocking) from errors (Red, blocking). Use a warning icon for cautions (“This may affect output”) and a stop/error icon for failures. Figma’s guide notes: use **red fill or border with an icon** for errors, and yellow/orange for cautionary notes. If a button click incurs cost or serious consequences, require a confirmation dialog with explicit label (e.g. “This will use credits. Continue?”) – AI-generated UIs often gloss over cost thresholds.  
- **Empty/No Data:** Design how each view looks when there’s nothing to show. Often this means a friendly illustration or message (e.g. “No episodes yet – start a new one”) and a primary action button. Don’t leave blank screens; even simple placeholder text or graphic is better than AI’s default empty div.  
- **Stale/Out-of-Date:** If content changes upstream and data is stale, indicate it. Common patterns: a yellow “stale” badge, or a faded card with a “Refresh” button/icon. For example, show a subtle sync icon if cache is old. Data tools (e.g. GitHub) mark outdated comments with an “Outdated” label – your workflow similarly needs a signal for stale state.  

In general, **design and document these states explicitly**. Include them as variants in your component library (e.g. Button: default/hover/disabled/error) and in style docs. Automating or documenting a state inventory (like the “UI Implementation Contracts” mentioned above) ensures you don’t rely on memory. 

# Progressive Disclosure for Experts

A pro tool must show only what’s needed for each task level. Follow UI best practices for complex apps: keep the default view uncluttered and reveal complexity on demand. For instance, hide advanced options in accordions or “Advanced Settings” toggles. Use **panel/inspector panes**: e.g. double-click or a sidebar to show detailed controls when an object is selected. Employ a **command palette** (invoked by hotkey) for rarely-used actions – this serves experts well without permanently crowding the UI. All of these are forms of staged disclosure. 

Concretely: keep the main screen focused on the current phase and its core fields. If certain fields or actions are only needed in corner cases, tuck them behind icons or “more” links. NN/g advises showing follow-up steps only after prerequisites are done. Apply this: for example, show sub-steps or additional filters only after the user chooses a main category. Many professional interfaces use fold-out sections, tabs or modal dialogs for secondary tools. If one user type is an expert (you), they can be given keyboard shortcuts or hidden panels; a novice (future viewer) sees a simpler initial interface. In short, design *with layers*: primary tasks always visible, advanced features a click or two away, and keep help/tooltips available for anything non-obvious.

# AI-Generated UI Critique Checklist

When an AI tool suggests a screen, evaluate it methodically:

- **Hierarchy and Spacing:** *Squint* at the layout. Do related items group by proximity? If you blur your eyes and the whole page blends to a uniform gray block, the design lacks hierarchy. Remove all borders mentally: the layout should still make sense by whitespace alone. If it falls apart, the AI design is “flat.” Check if primary elements (titles, key buttons, alerts) stand out with extra space or bold text.  
- **Visual Weight:** Ensure visual emphasis matches importance. An AI mockup may give a big empty panel more prominence than, say, the critical form field. As one NN/g study found, AI often highlights the wrong element. Ask: what catches your eye first? Is that really the highest-priority info? If not, adjust sizes/colors.  
- **Consistency:** Verify colors, fonts, and icon styles are consistent and purposeful, not random. AI UIs often use a variety of icon shapes or line weights; stick to one icon set. Check that disabled controls use a muted style and that button hover/pressed states are defined.  
- **Spacing Rhythm:** Beware “uniform everything” layouts. AI tends to space all elements equally, creating no rhythm. Look for monotonous grids – e.g. every margin exactly 8px. Good design alternates tight and loose spacing (tight for grouped data, loose around calls-to-action). If everything is equally padded, re-architect the spacing.  
- **Use of Icons and Graphics:** Icons should *explain* actions. If AI puts a generic “bell” or “gear” icon without context, replace it. Make sure icons match standard meaning or are labeled. Decorative borders or backgrounds that don’t add information should be removed (AI often adds frills that clutter).  
- **Content and Data:** Are the labels, numbers and placeholder text realistic? Many AI UIs use lorem text or repetitive gibberish. Replace dummy text with actual examples from your domain. Ensure tables and forms show real field names and sample entries.  
- **Interaction States:** Confirm all needed states are shown. Does it include an empty state (e.g. “no episodes yet”)? A loading spinner or progress bar for async actions? An error message template? AI screens frequently omit these, so flag any missing state.  
- **Accessibility Basics:** (Though not strictly design-only, check contrast and focus.) Ensure text is readable on the background (no light gray on white). Make sure interactive controls are large enough and have focus outlines for keyboard use.  
- **Flow Coherence:** For multi-step flows, ensure the navigation between screens is clear. The AI might produce disjoint pages; verify back buttons or breadcrumbs.  

Use this checklist like a code-review: iterate through the UI and mark any violation (e.g. “no visual hierarchy”, “missing disabled state”, “icon meaning unclear”). AI tools often get the “surface” right but miss such details, so highlight those gaps.

# Prompting Playbook

To guide AI into useful designs, use **specific constraints and references** rather than vague language. From UX research on AI tools:

- **Explicit Styles or Frameworks:** Invoke a visual style by name. E.g. “Design in a *neobrutalist* style” or “using a *glassmorphism* look”. This is far more effective than saying “modern” or “simple.” Similarly, name UI frameworks (Material, Carbon) or brand fonts if relevant, but avoid outright copying a brand’s identity – better to adapt a recognized style.  
- **Attach Visual References:** Whenever possible, provide image examples or sketches. A low-fi mockup, a mood board, or even screenshots of competitor tools will steer the AI’s creativity. For instance, Figma Make can “see” a pasted screenshot of a Material Design component set and tend toward that style. This is how you transfer your visual intent without lengthy text prompts.  
- **Include Mock Data:** Give the AI realistic content. If you have the actual JSON or text strings that your UI will display, include them (or ask it to generate sample data first). The NN/g study recommends this to ensure layouts fit the real content. For example, prompt: “Use this sample list of episode titles and dates: […]” – the AI will place and size elements to fit.  
- **Use Tokens or Code:** Since you have a codebase, you can feed the AI direct context. Some design tools let you attach code snippets. For example, provide the CSS tokens or a component’s HTML/CSS as context. Claude Design’s workflow even lets you import your own code as a design reference. This anchors the AI to your existing styles.  
- **Iterate via Chat:** Use the AI itself to improve your prompts. For example, ask ChatGPT to *analyze* a reference design and list its visual features; then incorporate those keywords in your prompt. Or have it review your prompt for missing details. You can also task it with generating code snippets for particular components (e.g. “give me a JSON schema for an episode object” or “produce a CSS snippet for a warning alert box”).  
- **Request Variants Intelligently:** Don’t just ask for “3 variants” on the same vague prompt. AI will often return near-duplicates. Instead, make each variant prompt distinct. Example: “Now design the screen as a dark theme version” or “Alternate layout: sidebar on left vs on top.” Changing one key parameter per prompt forces diversity. In short, adjust the constraint (layout, color scheme, feature emphasis) for each version.  

**What doesn’t work:** Generic adjectives (“clean, sleek”), unspecified comparisons (“like popular apps”), or repeating the same prompt for variants. Also, feeding only text without context often leads to “Frankenstein” UIs with clutter and repetition. Be precise, be visual, and be iterative. Each refinement (and even “critique loop” with the AI) should bring you closer to a professionally coherent design.

# Coherence Over Time (Maintaining the System)

To keep your UI consistent as you code:

- **Tokens as Single Source:** Use design tokens (CSS variables or a tokens file) for all colors, fonts, spacing. Automate syncing them with any design tool if possible. Automated token pipelines (Figma Variables ↔ code) prevent “token drift”. As one guide notes, only ~40% of teams have such pipelines – without it, color or spacing values will slowly diverge. Enforce token use via CSS lint rules or build-time checks.  
- **Component Inventory:** Maintain a living catalog (Storybook or similar) of your components. For each component, list its variants and states. Regularly audit to remove unused ones and avoid duplicates. A good practice is visual regression testing: use tools like Chromatic or Percy in your CI to catch any unexpected UI changes on every PR. Also do a periodic **design QA** – e.g. before a release, compare key screens against your design specs (possibly via screenshot diff or OverlayQA).  
- **Drift Detection:** Expect drift – proactively detect it. OverlayQA’s report on “design system drift” identifies five drift types: tokens, variants, patterns, docs, and behavior. Use tools accordingly: e.g. compare Figma token values vs CSS, run stylelint to catch hardcoded values, inspect production CSS for orphaned values. A visual regression test in CI will catch any layout or style drift against the last known-good design, though you’ll still need manual review to tie changes to the spec. Schedule such audits regularly (at least quarterly, or monthly if you’re pushing code fast).  
- **Governance and Rituals:** Include design review as part of your normal workflow. For example, add a step in code reviews: “Does this match the design system?” Designers should review PRs for visual changes. Freeze major design tokens before big sprints to avoid conflicting updates. Document how to add new tokens/components and hold a quick sync (maybe a monthly meeting or Slack check-in) to coordinate any changes. Over time, the easiest things to let slip are often docs and tokens. Keep your documentation (even a single README of styles) up-to-date when you make CSS changes, otherwise “documentation drift” happens.  

The **rot** usually starts with little inconsistencies: a component instance gets detached and tweaked in one screen (pattern drift), or someone hardcodes a color instead of using the token (token drift). Catch these early by checking token coverage and reviewing component usage. Visual regression and token linting are your guards against slow decay.

# Failure Modes and Lessons

Using AI and code-driven design brings its own pitfalls. Be aware of these common failure modes (learned from real teams):

- **Skipping the fundamentals:** AI isn’t magic – it *exposes* holes in your process. For example, Dropbox designers found that if components weren’t built with the design system (e.g. missing tokens or auto-layout), Figma Make “struggled” to generate them accurately. In other words, design shortcuts you thought hidden will break the AI pipeline. Lesson: invest in a proper design system (tokens, constraints) *before* pushing AI tools too hard.  
- **Generic, uninformed output:** Relying on broad prompts leads to “Frankenstein” UIs (cluttered, disjoint). If you generate code without review, it can end up in production as low-quality. At Dropbox, one designer did ship Cursor-generated code, but *only after engineers refactored it heavily*. Assume AI output is a draft – plan human polish and testing.  
- **Neglecting edge states and responsiveness:** AI prototypes often miss empty/error states and non-desktop views. Unless you explicitly prompt or design them, you’ll notice gaps late. Always check for these cases.  
- **Neglecting collaboration:** Tools alone don’t solve process. Without coordination, multiple teams will drift apart. AI may speed up tasks, but you still need “internal champions” and workflows. (One report noted that without mandates and support, adoption lags.) Make sure you and your future collaborators have access and buy-in to the tools and DS.  

**If starting over, what to do differently?** Focus on getting the basics right first. Build a small but solid design system (even one-person, it pays off) and automate token sync. Use AI to augment design, not replace judgement. Plan for integration: for instance, a developer at Dropbox built a custom server so Cursor could read the exact design tokens from their system – you won’t necessarily do that, but it illustrates bridging the gap early. And always treat AI results as a brainstorming partner: generate a draft, then critically refine it by hand. Over-reliance on AI without critique leads to bland or broken designs. Finally, learn continuously: test your UI with actual users (you!) and iterate the design system as you go. 

By following a structured process, defining your visual language up front, and using AI tools judiciously (with careful prompting and review), you’ll create a tool UI that feels intentional and robust.
